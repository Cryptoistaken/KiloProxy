## 02 â€” VpnService usage, onBind/onRevoke & AIDL binding

1. **HIGH** | NEEDS-FIX | `SocksVpnService.onBind()` (`SocksVpnService.kt:351-358`) ignores the `Intent` action and returns the custom AIDL `VpnBinder` (`mBinder`, decl. `SocksVpnService.kt:125`) for **both** the system UID and the app's own UID â€” it never returns `super.onBind(intent)`. The VpnService contract requires returning the framework's internal binder for the `SERVICE_INTERFACE` (`android.net.VpnService`) bind; the system binds through that binder to deliver revocation. Returning the app's AIDL binder to the system breaks `onRevoke()` (`SocksVpnService.kt:345-349`, which calls `stopMe("vpn_revoked")`): when the user disconnects/revokes via system Settings, the callback never fires, the service stays "connected" (notification/UI), usage isn't persisted, and teardown only happens indirectly via tun-fd close â†’ tun2socks monitor. | `vpnservice-ref.html` onBind section (lines ~45011-45014): "This method returns null on Intents other than SERVICE_INTERFACE action. Applications overriding this method must identify the intent and return the corresponding interface accordingly." | Restore the canonical pattern: `if (intent?.action == VpnService.SERVICE_INTERFACE) return super.onBind(intent)` for the system bind; return the custom AIDL binder only for `Binder.getCallingUid() == Process.myUid()`; `null` otherwise.

2. **LOW** | WARN | `VpnService.prepare()` is correctly gated before `establish()` on every entry path: `VpnViewModel.prepareAndStartVpn` (`VpnViewModel.kt:307`), `StatusScreen.kt:129/278`, `ProfileFragment.kt:594`, `FloatingControlService.kt:826,873`, `BootReceiver.kt:17`. `establish()` runs on the main thread in `configure()` (`SocksVpnService.kt:599`) and the null result is handled (`:600-604`, teardown `:332-334`) â€” no crash when unprepared/revoked. **However `VpnService.protect()` is never called on any socket** (docs step 2 skipped). This is mitigated: the app excludes its own UID from the tunnel via `addDisallowedApplication(packageName)` (`SocksVpnService.kt:558-596`), so the native SOCKS client, pdnsd, and ip-api probes bypass the tun and no circular route forms. | `vpnguide.html` (lines ~8907-8910): "Call VpnService.protect() to keep your app's tunnel socket outside of the system VPN and avoid a circular connection"; `vpnservice-ref.html` prepare() (lines ~45073+); guide: "establish() returns null if your app isn't prepared or somebody revokes the permission" (~8968-8972). | Optional hardening: also `protect()` the Java-side sockets (SOCKS probe / ip-api `HttpURLConnection`) instead of relying solely on UID exclusion â€” exclusion stays anyway because the native tun2socks runs under this UID.

3. **LOW** | OK | Manifest declaration is correct: `AndroidManifest.xml:33-44` declares `android:permission="android.permission.BIND_VPN_SERVICE"`, `android:exported="true"`, intent-filter action `android.net.VpnService` (SERVICE_INTERFACE), `foregroundServiceType="specialUse"` with `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`. BIND_VPN_SERVICE is a signature-level permission, so `exported=true` is safe (only the system can bind) and is required for the system to bind the service. | `vpnservice-ref.html` class description (lines ~32874-32885): "Services extending this class need to be declared with an appropriate permission and intent filter. 4. **MED** | NEEDS-FIX | The UI ViewModel binds once in `init` (`VpnViewModel.kt:108` â†’ `bindToService` `:113-120`) and never rebinds: `onServiceDisconnected` only nulls the binder (`:99-102`), `onBindingDied` (API 26+) is not overridden, and `startPolling` forces `clearState()` (disconnected UI) whenever unbound (`:203-205`). If the `:vpn` process is killed by LMK and restarted via START_STICKY, the main UI permanently shows "disconnected" and can neither stop nor restart the live VPN. Contrast: `FloatingControlService.kt:879-887` implements `scheduleRebind()` and self-heals. Compounding: a null-intent START_STICKY restart returns 0 without re-establishing the tunnel (`SocksVpnService.kt:288-290`). | `ServiceConnection`/`Service` docs â€” a one-shot `bindService` is not re-delivered after the bound process dies; `onBindingDied(ComponentName)` (API 26+) covers binder-killed cases. | Override `onBindingDied` and re-bind in `onServiceDisconnected` (call `bindService` again, optionally with `BIND_ABOVE_CLIENT`), and re-sync state on reconnect; also handle null-intent restarts by re-establishing from the last profile or `stopSelf()`.

Summary: onBind returns the wrong (custom AIDL) binder to the system, violating the documented SERVICE_INTERFACE contract and breaking onRevoke (HIGH); prepare() is correctly gated on all start paths while protect() is omitted but mitigated by UID exclusion; the manifest service declaration is correct; the Compose UI never rebinds a dead AIDL connection, leaving stale state after a :vpn process death (MED).

## 12 -- Diagnostic: floating bubble not restored on app close -> reopen (root cause + fix)

### Symptoms
- User closes the app with the floating bubble ON, reopens it, and the bubble does not come back.
- Expected: bubble enabled/disabled state is remembered and re-applied on reopen (and, ideally, on boot).

### Root cause (established by read-only diagnosis)
1. The on/off pref (`floating_control`) IS persisted and IS NOT cleared on close (the service's onDestroy never writes it).
2. MainActivity.onCreate DOES contain a restore path -- but only on Activity cold start.
3. The prior bugs:
   - No boot restore in BootReceiver.onReceive (VPN-only branch).
   - The notification-permission gate in the restore was an empty-callback dialog (result discarded).
   - Potential double-start race between STICKY service restart and the Activity restore path.

### Fix applied (in batch above, fix 09)
- Boot: BootReceiver reads PREF_FLOATING_CONTROL and, if true + canDrawOverlays, starts FloatingControlService via the companion start(context) (already handles API <26/>=26).
- Cold launch: MainActivity.onCreate calls startFloatingControlIfPersisted() (MainActivity.kt:43-53): returns early if pref off or overlay not allowed; requests POST_NOTIFICATIONS when API 33+ and not granted (starts anyway); grant callback re-invokes the idempotent routine.
- Double-start guard: FloatingControlService.onStartCommand (FCS:215-220) returns START_STICKY when bubbleView?.isAttachedToWindow == true -- one window only.

### Result
- Bubble enabled -> close (swipe/kill) -> reopen -> bubble restored.
- Bubble enabled -> reboot -> bubble restored on boot.
- Bubble disabled -> no bubble on reopen or boot.
- Engine files untouched; SettingsScreen/Keyboard logic/toggle paths unchanged.
